# ClipCheck — Master Design Document

Status: draft v0.1 · Target: Windows 10 2004+ / Windows 11 x64

This is the top-level design. Each feature has a deep-dive in `docs/design/`; the cross-cutting decisions live in [00-brief](docs/design/00-brief.md) and win in any conflict.

## 1. Goals and non-goals

**Goals**
1. Record only the detected game's video, automatically, with negligible overhead.
2. Support a *full session* recording and *Past N minutes* clips simultaneously.
3. Multiple clip hotkeys with independent durations.
4. Multi-track audio (per-app tracks, separate mic), all PC audio captured.
5. Configurable encoder, codec (H.264/H.265, optional AV1), bitrate/quality.
6. Local gallery, player, rename, filter/sort, and a fast clip trimmer.
7. Very light: Rust service idling < 15 MB, no Electron.

**Non-goals**: uploads, accounts, sharing, social feeds, streaming, overlays/injection (v1), Linux/macOS (v1).

## 2. Language and stack decision

| Option | Verdict |
|---|---|
| **Rust** | **Chosen.** Memory-safe, no GC pauses in a real-time capture path, tiny binaries, first-class `windows` crate for WGC/WASAPI/D3D11, easy FFI to FFmpeg. |
| C++ | Equivalent performance, but memory-safety risk in a long-running always-on process and slower iteration. |
| C# / .NET | Heavier runtime, GC jitter in the frame path. |
| Electron | Violates the lightweight goal (100+ MB idle). |

UI is **Tauri v2** on the system WebView2 (already on Windows 11), so the UI adds no bundled browser. Crucially the *recorder is a separate headless Rust process* (`clipcheckd`), so the UI can be closed and the recorder stays at a few MB. WebView2 also gives a real `<video>` player for free (scrubbing, volume, HEVC via OS decoders).

## 3. System architecture

```
 ┌────────────────────────── clipcheckd (Rust, tray, no webview) ──────────────────────────┐
 │ detect ─► capture(WGC) ─► NV12 ─► encode(HW/SW) ─┐                                       │
 │ audio: per-app loopback x N + mic ─► AAC/Opus ───┤  EncodedPacket stream                 │
 │                                                  ├─► buffer  (GOP-aligned segment ring)  │
 │ hotkeys ─► "clip last N" ───────────────────────►│        └─► clip extract (remux)       │
 │ IPC server (named pipe)                          └─► session (full-session writer)       │
 │                                                          └─► library.index(file)        │
 └──────────────────────────────────────────────┬───────────────────────────────────────────┘
                                                │ named pipe (JSON)  +  SQLite (WAL)
 ┌─────────────────── clipcheck UI (Tauri v2 + Svelte) ────────────────────────────────────┐
 │ Gallery · Player/Trimmer · Live status · Settings        clip:// protocol (range reads)   │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
```

### Key principle: encode once, fan out
Video and audio are encoded a single time. The same packet stream feeds (a) the rolling segment buffer and (b) the full-session file writer. Therefore a full session and past-N clips cost one encode, and a clip hotkey during a session just remuxes already-encoded segments.

## 4. How each requirement is met

| Requirement | Design | Doc |
|---|---|---|
| Auto-detect games, auto-start | Process + window heuristics, known-games DB, store library scan, allow/block lists | 01 |

| Full session / Past N | Same packet stream, two sinks | 05, 06 |

| Multiple clip hotkeys | `[[hotkeys.clip]]` array of {name, keys, seconds} | 05, 09 |
| Split mid-session, new session immediately | Keyframe-aligned rotation, zero gap, same session id, part N+1 | 06 |
| Stop session any time, save footage | Finalize + index; buffer continues if enabled | 06 |
| Per-app audio tracks + mic track | Track routing rules, process-loopback sources | 04 |
| Encoder / codec / bitrate config | Probe + Auto/forced, presets + custom | 03, 09 |
| Storage location | `storage.root`, per-game folders, move-or-leave on change | 07 |
| Watch clips in app | Tauri + `<video>` + `clip://` range protocol, multi-track audio via Web Audio | 08 |
| Rename in app | Atomic file+DB rename, collision-safe | 07 |
| Filter/sort | Indexed SQLite queries, pagination | 07 |
| Volume, scrubbing, clip shortener | Player + lossless keyframe-snapped trim, optional precise re-encode | 08 |

## 6. Principal risks

| Risk | Mitigation |
|---|---|
| Exclusive-fullscreen games not capturable via WGC | Recommend borderless; v2 game-hook path (OBS-style), designed in 02 |
| Anti-cheat flags injection | v1 uses no injection at all |
| Process-loopback needs Win10 2004+ | Fallback: single system-mix track, noted in UI |
| HEVC playback in WebView2 depends on OS codec | Detect, offer proxy transcode (08) |
| Copyleft code or binaries entering the project | Project is Apache-2.0 (D61); FFmpeg is neither shipped nor downloaded (D58), only an optional test oracle; `deny.toml` allows permissive licenses only (`docs/LICENSING.md`) |
| A/V drift over hours | Single QPC clock, drift correction (04) |
| Disk fill from long sessions | Quota, free-space guards, auto-split (06, 07) |

## 11. Implementation decisions made during build
| # | Decision |
|---|---|
| D14 | **Encoder backend v1 = `ffmpeg.exe` child process** (raw NV12/BGRA frames on stdin, fMP4 segments out), behind an `Encoder` trait. In-process libav (doc 03) is a later optimization; the trait keeps callers unchanged. |
| D15 | FFmpeg build: BtbN `n8.1` win64 GPL shared (SHA-256 `4468dc0e…26644`), vendored (git-ignored) under `vendor/ffmpeg/`. Supersedes the 7.1 pin in doc 03. |
| D16 | v1 capture does a CPU readback (staging texture, BGRA) per frame. The zero-copy GPU path (doc 02/03) is a later optimization. |
| D17 | Dev machine: RTX 5080 (NVENC H.264/HEVC/AV1 verified) + AMD iGPU (hybrid-GPU test case). |
| D18 | **Sessions are assembled from the encoder's keyframe-aligned segments**: finished segments are hard-linked into a session dir and losslessly concatenated (`-c copy -movflags +faststart`) on stop/split/game-exit. Splits are therefore zero-gap. Crash recovery = concat leftover segments at startup. Replaces the incremental fMP4 session writer of doc 06 for v1. |
| D19 | Past-N clips = lossless concat of the buffer's last segments (`ClipPlan`) via ffmpeg concat demuxer with `-c copy` and a start trim; keyframe-snapped. |
| D20 | **WinRT/MTA lifetime:** the `windows` crate caches activation factories process-wide; capture holds a process-lifetime MTA via `CoIncrementMTAUsage` (no `RoUninitialize`). Without it, the second capture in a process crashed in `GraphicsCaptureSession::IsSupported()`. Any new crate using WinRT must do the same. |
| D21 | Named-pipe handles are **overlapped** and `PipeConn` is cloneable, so the daemon pushes events to idle subscribers from a dedicated writer thread (single writer lock per connection). |
| D22 | Daemon reports `idle` (not `degraded`) while the encoder probe is still running; `degraded` is reserved for real failures (no FFmpeg, probe failed). |
| D23 | Concat paths (`SessionAssembler::finalize`, `extract_clip`) use `-map 0` and re-apply audio track titles read from the first segment (mp4 stores them as the `name` tag). |
| D24 | **Storage layout & libraries.** New recordings go to the PRIMARY location as `<root>\Clips\<Game>\…` and `<root>\Sessions\<Game>\…` (like Medal's `Clips\<Game>`). Any number of EXTRA library folders are indexed in place (never moved; scanned incrementally in the background; a missing drive marks the library offline, not the clips deleted). Importing COPIES files into `<primary>\Clips\<Game>\` after a free-space check, with a visible 'uses extra space' warning. Junk is skipped (`$R*`/`$I*`/`$RECYCLE.BIN`, `Thumbnails`, `Temp`, `Video-Editor`, `Databases`). Clip date = file mtime; game = parent folder name under the root (or the filename/`Imported`/`Unsorted` fallback). |
| D25 | **In-app player (implemented).** Recordings play inside the app through the `clip://` scheme (`http://clip.localhost/rec/<id>`, `/aud/<id>/<n>`), served by `apps/ui/src-tauri/src/media.rs` (HTTP Range, 8 MiB chunks, paths resolved from the library DB only). `apps/ui/src-tauri/src/player.rs` probes with ffprobe and, for 2+ audio tracks, extracts each track to a cached `.m4a` sidecar, because WebView2 exposes only the first audio track. The UI (`apps/ui/src/lib/player/model.ts`, `mixer.ts`, `apps/ui/src/lib/Player.svelte`) mutes the video and plays the sidecars through one Web Audio gain node per track. Controls: volume, mute, speed, track audible/solo/gain. MKV is served but flagged not playable. Spec: `docs/impl/player-mvp.md`. |
| D26 | **Trim execution (implemented, tested).** `crates/clipedit/src/run.rs`: `build_args` (pure), `run_trim` (cancellable ffmpeg child, `-progress pipe:1` parsed at ~4 Hz, 200 ms throttle), `parse_progress_line`. Lossless stream-copies from the keyframe at or before the start with `-map 0 -map_metadata 0`; precise re-encodes video from the keyframe and copies audio. The temp output is `<dst>.part` with an explicit `-f` muxer chosen from the destination extension (mp4/m4v -> mp4, mov, mkv -> matroska) and is renamed on success; the source is never touched and an existing destination is refused. MP4 stream copy drops audio track titles, so they are re-applied from the source (same approach as `buffer::extract`). Verified against real ffmpeg by an independent tester (15 tests). Not yet reachable from the app: the Tauri command is D27. |
| D27 | **Trimmer UI (frontend implemented, backend pending).** `apps/ui/src/lib/player/trim.ts` (pure selection/timecode/snap-readout logic), `trimapi.ts` (typed wrappers) and `Trimmer.svelte` exist. | D28 | **Update UX (implemented, frontend tested).** Backend: `apps/ui/src-tauri/src/updater.rs` provides `check_for_update`, `install_update`, `skip_update_version`, `get_update_state` and emits `update-available`, `update-progress`. | D29 | **Audio starvation guard (implemented, tested).** `silence_deficit(elapsed, written_samples, sample_rate, channels) -> usize` in `crates/encode/src/audio_in.rs`: the writer thread injects paced silence (capped at 100 ms per tick, 1 s deficit cap) when a connected sink queue has been empty for more than 100 ms, never after finish and never ahead of real data. | D35 | **Partial hotkey registration.** In `crates/hotkeys/src/win.rs`, a binding the OS refuses is reported as a `RegisterFailure` and the other bindings stay active. The daemon logs and publishes one warning per refused chord (`apps/clipcheckd/src/service.rs`, `warn_hotkey_failures`). |
| D36 | **Storage libraries and `[updates]` config.** Extra library folders are indexed in place (see D24). `[updates]` in `crates/core/src/config/schema.rs`: `check` defaults to `"notify"` (`"never"` makes no background network calls), `channel = "stable"`, `interval_hours` defaults to 12 (1..=168, used only with `notify`), `endpoint` overrides the manifest URL. `updates.interval_hours` is the authoritative key. The older `updates.check_interval_hours` is gone from code. |
| D37 | **FFmpeg as a downloadable pack.** Store: `%LOCALAPPDATA%\ClipCheck\ffmpeg\<ver>\bin`, where `ffmpeg\current.txt` names the active version (`crates/encode/src/locate.rs`; layout in `crates/update/src/pack.rs`). `locate_ffmpeg` order: `CLIPCHECK_FFMPEG`, the pack, `<exe dir>\ffmpeg\bin`, `vendor/ffmpeg/*/bin`, then `PATH`. | D38 | **Shutdown `reason` and `exe_path` safety.** IPC `Shutdown { reason }` (`crates/ipc/src/proto.rs`). `reason: "update"` is refused with `busy` while a recording session exists (`apps/clipcheckd/src/server.rs`); the replay buffer alone does not count. | D41 | **FFmpeg is bundled in the installer (supersedes the install-time part of D37).** `bundle.resources` in `tauri.conf.json` ships ffmpeg, ffprobe and the 7 shared DLLs from `vendor/ffmpeg/<build>/bin` to `<install dir>fmpegin`, which `locate_ffmpeg` already searches (exe dir, after the pack store). Release CI must supply `vendor/ffmpeg` (see `scripts/release/package-ffmpeg-pack.ps1`). |
| D42 | **FiveM and wildcard name patterns.** Exe lists and the known DB accept `*` and `?` (`crates/detect/src/lists.rs` `glob_match`, `NameSet`; `crates/detect/src/known_games.rs`). Known DB patterns: `FiveM*GTAProcess.exe` and `FiveM*GameProcess.exe` (`FiveM`), `RedM*GameProcess.exe` (`RedM`). `PlayGTAV.exe` is a built-in launcher. Known-window rule in `score.rs`: a known exe with a visible window of at least 1280x720, a non-generic title and no penalty is accepted without fullscreen or GPU evidence (replaces the strict windowed rule in 01-game-detection.md 5.11, pending owner confirmation). `game_id` per build and `should_record` exact matching are unchanged (`apps/clipcheckd/src/service.rs`, follow-up). |
| D43 | **Video timeline follows the wall clock.** The live pipeline starts ffmpeg with `FrameClock::Wall` (`crates/encode/src/pipe.rs`): `-use_wallclock_as_timestamps 1 -framerate <fps>` on the raw stdin input (never an input `-r`, which regenerates timestamps by count) and `-fps_mode cfr -r <fps>` on the output, so ffmpeg duplicates or drops frames to hold constant fps against real time. Before this, raw frames were numbered by count, so a capture or encoder delivering about 36 fps into a 60 fps stream gave video about 1.7x too short, played too fast, and the muxer throttled the real-time audio the same way. Offline feeds and tests keep `FrameClock::Count` (the default). Regression: `crates/engine/tests/pacing_tests.rs`. |
| D44 | **Tap and long-press clip hotkeys share a chord.** `[[hotkeys.clips]]` gains `press = "tap" \| "long"` (default tap). Core: `schema::Press`, `schema::LONG_PRESS_MS = 400`. Validation (`config/validate.rs`, CFG-H002) allows one tap and one long clip on the same chord; every other shared chord conflicts. Hotkeys: `PressKind`, `Binding.press`, `HotkeyRegistry::build` applies the same rule and `Registry::lookup_press`. Each distinct chord is registered with `RegisterHotKey` once. A pure `gesture::GestureTracker` decides the event: a tap-only chord fires on press, a chord with a long binding fires at the threshold, and a chord with both fires the tap on release if shorter than the threshold. The hold is polled every 10 ms via `SetTimer` only while pending (`win.rs`). `HotkeyService::start_with_threshold` takes the threshold; `start` keeps 400 ms. Why: one key should give a quick clip and a longer-hold clip without two keys. Tap latency is the cost: a shared chord's tap saves on release. Settings doc 09 and hotkeys doc 05 updated. Tests: `crates/core/tests/press_tests.rs`, `crates/hotkeys/tests/press_registry_tests.rs`. |

| D46 | **Process model: one recorder process, no `--worker` (supersedes D3; issue #198).** The shipped design is a single executable: `ClipCheck.exe` is the UI and `ClipCheck.exe --daemon` is the recorder (tray, IPC server, detection, hotkeys and the recording service thread with the engine's capture, audio, tracker and clip threads). The supervised `clipcheckd --worker` child of doc 10 (§2, §5.1, §5.5, `RestartWorker`, `WorkerRestarted`, worker heartbeat) is **not** built and is not planned for v1. Why: the code that is most likely to crash or hang, the encoder, already runs out of process (`ffmpeg.exe` child, D14); a second process would need a second IPC protocol, a frame/segment hand-off and a supervisor, for little gain. Crash consequences, accepted: a panic on the service thread or a fault in WGC/D3D/WASAPI code takes the recorder (and the tray) down.
